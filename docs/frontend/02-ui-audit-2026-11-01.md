## 1. Executive summary

PageWise already has a substantial student-facing UI foundation:

- The app shell has a desktop sidebar, mobile drawer, theme toggle and user menu.
- Study has Biology / Physics / Chemistry and Class 11 / 12 selection, chapter cards, Continue Studying, Recent Chapters and progress indicators.
- The chapter workspace uses the custom PDF.js viewer beside a page-specific question panel.
- Focus and List question modes, answer feedback, bookmarks and basic page navigation exist.
- Sign-in, Settings, Progress and Bookmarks have usable first versions.

The next week should improve these existing experiences rather than rebuild them. The highest-value work is the Study workspace, PDF controls/states, responsive behavior and consistent components.

## 2. Findings

### P1 — Resolve design-token documentation drift

**Evidence**
- `docs/frontend/01-design-foundations.md` specifies a warm neutral / emerald palette (for example canvas `#FAFAF7`, dark canvas `#0C1210`, brand `#148062`) and describes `field` as a control-border token.
- `src/app/globals.css` currently ships a slate / blue palette (for example canvas `#F8FAFC`, dark canvas `#0B1120`, brand `#2563EB`) and uses `--field` as a pale fill.
- `scripts/check-contrast.py` checks the shipped slate / blue values, not the palette documented in design foundations.
- `src/app/layout.tsx` still sets theme-color metadata to the older warm-green canvas values.

**Impact:** Designers and contributors cannot tell which palette and token semantics are authoritative; browser chrome can also differ from the actual page surface.

**Recommendation:** Make one explicit design decision before token changes. Either bring the shipped CSS and contrast matrix back to the approved emerald foundation, or update the design foundation and viewport theme colors to formally adopt the current slate / blue system. Do not mix both systems.

### P1 — Control borders do not follow the documented token semantics

**Evidence:** Profile fields in `src/features/profile/profile-form.tsx` and the printed-page input in `src/features/study/study-workspace.tsx` use `border-line`. The design foundation says `line` is for decorative dividers/card edges and that controls need the higher-contrast `field` border token.

**Impact:** Inputs and selects may be harder to distinguish from their surrounding surfaces, particularly in dark mode and for users with low vision.

**Recommendation:** After resolving the token drift, standardize input, select and other interactive borders on the approved control-border token. Keep decorative card edges on `line`.

### P1 — Study split pane is not resizable

**Evidence:** `src/features/study/study-workspace.tsx` uses a fixed CSS grid ratio at desktop widths. The PDF viewer can be hidden and the sides can be swapped, but there is no draggable divider.

**Specification:** `docs/blueprint/09-pdf-viewer-spec.md` calls for a draggable, keyboard-accessible divider.

**Impact:** Students cannot allocate more room to a dense NCERT page, a diagram or a long question.

**Recommendation:** Add a keyboard-operable split-pane divider with sensible min/max widths. Preserve the existing default: questions left, PDF right. Keep Swap sides as an explicit alternative.

### P1 — PDF loading and error states are too basic

**Evidence:** `src/components/viewer/pdf-viewer.tsx` renders plain text for loading and failure. The failure message has no retry or report-problem action. The page placeholders are blank until their canvases render.

**Specification:** `docs/blueprint/09-pdf-viewer-spec.md` calls for per-page skeletons and retry/report actions; `docs/blueprint/02-screens-spec.md` also requires retryable error states.

**Impact:** A slow or failed PDF looks unfinished, and students have no clear recovery path.

**Recommendation:** Add page-shaped loading skeletons, a clear retry action and a non-technical error message. Keep technical details available for diagnostics rather than exposing raw errors.

### P1 — Workspace toolbar is dense on phones

**Evidence:** The workspace toolbar in `study-workspace.tsx` keeps Back, chapter title, previous/next, page label, printed-page input, zoom, follow-reading, invert-pages and upload actions in one wrapping row. Several controls can create multiple toolbar rows on narrow screens.

**Impact:** The toolbar can consume a large portion of a phone's viewport, leaving less room for reading and answering questions.

**Recommendation:** Group controls by task. On mobile, keep only the most-used controls in the primary row and move secondary actions into a compact overflow/control sheet. Keep page navigation available in both Read and Practise modes.

### P2 — Mobile drawer needs complete keyboard interaction

**Evidence:** `src/components/app/app-shell.tsx` opens and closes the drawer by button, overlay or navigation. It does not implement Escape-to-close, focus trapping or focus restoration.

**Specification:** The design foundation requires the mobile menu to close on Escape.

**Recommendation:** Treat the drawer as a modal navigation surface: close on Escape, keep focus inside while open, restore focus to the menu trigger on close, and prevent background scrolling.

### P2 — Mobile Read / Practise tabs need stronger semantics

**Evidence:** Workspace tabs use `role="tablist"` and `role="tab"`, but do not connect tabs to tab panels through IDs / `aria-controls`, and do not implement arrow-key tab navigation.

**Recommendation:** Complete the tab pattern (including selected/focus behavior and associated panels), or use a simpler button group with pressed states if full tab semantics are not needed.

### P2 — Focus-mode progress indicators rely on colour alone

**Evidence:** The question dots in `study-workspace.tsx` are hidden from assistive technology and use only colour to indicate current, correct, incorrect or unanswered state.

**Specification:** Design foundations require states to have a non-colour cue.

**Recommendation:** Give each indicator a visible shape/icon or concise status label, and an accessible name such as “Question 2: answered correctly”.

### P2 — List mode lacks the specified sticky summary

**Evidence:** List mode renders the question cards in a scrollable pane but does not show the sticky answered / correct summary described in `docs/blueprint/02-screens-spec.md`.

**Recommendation:** Add a compact sticky summary above the scrollable question list. It should reflect real session state, not placeholder values.

### P2 — PDF controls are missing several specified affordances

**Evidence:** The current toolbar supports previous/next, printed-page jump and zoom plus/minus. It does not expose fit-to-width / reset zoom, single-page mode or the documented `+`, `-`, `0` shortcuts.

**Recommendation:** Add only the controls that remain useful with the current continuous-scroll viewer: a clear Fit / Reset action and keyboard zoom shortcuts. Treat single-page mode as a separate product decision rather than adding it without testing.

### P2 — Empty states are mostly plain text

**Evidence:** Empty states in Practice, Progress and Bookmarks are text-only. The Study no-chapters state has a heading and explanation but no clear action.

**Specification:** `docs/blueprint/02-screens-spec.md` asks for an icon, one sentence and one primary action.

**Recommendation:** Standardize a reusable EmptyState component with a clear next step. Keep copy honest when content or data is not available.

### P2 — Some server-data failures can look like empty content

**Evidence:** Study, Practice, Progress and Bookmarks pages commonly fall back to `data ?? []` without rendering a distinct query-error state.

**Impact:** A database/network failure may be presented as “no chapters” or “nothing saved”, which is misleading.

**Recommendation:** Distinguish query failure from a successful empty result and provide a safe retry path.

### P2 — Progress table needs narrow-screen handling

**Evidence:** `src/app/(app)/progress/page.tsx` renders a four-column table without an explicit horizontal-scroll wrapper or alternate compact layout.

**Recommendation:** Test at 360 px and keep the table usable without clipped columns. An `overflow-x-auto` wrapper is an acceptable first step.

### P3 — Layout preferences are not persisted

**Evidence:** `swap`, `showViewer`, `zoom` and question mode are local component state in the workspace. They reset on a fresh visit.

**Specification:** The PDF viewer spec says swap / hide / resize preferences should persist.

**Recommendation:** After core interactions are stable, persist only durable preferences (for example split ratio, side order and default mode) in user preferences. Avoid persisting temporary session state unnecessarily.

## 3. Intentional omissions — do not treat as Day 1 defects

- Chapter search and global search were explicitly omitted from the current Home / app-shell build because search backend functionality is not ready.
- Chapter-level tests, timed tests and results belong to a later Practice milestone; the current Practice page honestly routes students to page-wise practice.
- Full Home redesign, leaderboards, social features, offline mode and AI assistant are outside this one-week UI pass.
- Subject/Class selector and the main Study dashboard already exist; do not rebuild them.

## 4. Existing strengths to preserve

- Skip-to-content link and visible focus outline exist at the app root.
- Inter is self-hosted; theme handling uses `next-themes`.
- App shell has distinct mobile and desktop navigation.
- Study uses a custom PDF.js viewer rather than an iframe.
- The viewer caps concurrent render tasks and keeps reading position through zoom/layout changes.
- Question cards show textual correct / incorrect feedback and explanations.
- Subject/Class selection is URL-addressable and signed-in preferences are saved.
- The current Home and Practice copy avoids pretending that unbuilt search, notification or chapter-test features already exist.
